## P1-S3-FE-01: Workflow Trigger — Block Detail Action Button

**Description:** Add a "Start Client Onboarding" action button to the block detail page. This is the primary gap from Sprint 2 — the design partner walkthrough could not trigger a workflow because no UI trigger existed. FE-03 (Sprint 2) shows workflow status but has no trigger. This task adds the trigger.

**Button behaviour:**
- Visible when `block.type === 'client'`
- Calls `POST /api/actions/onboarding.start` with `{ blockId, clientName: block.name, jurisdiction: block.metadata?.jurisdiction || 'AU' }`
- Loading state: button disabled + spinner during request
- Success: toast "Onboarding workflow started" + navigate to `/workflows`
- Error: toast with error message; button re-enabled

**Acceptance Criteria:**
- [ ] "Start Client Onboarding" button rendered on block detail page for client-type blocks
- [ ] Button calls `POST /api/actions/onboarding.start` with correct payload
- [ ] Button shows loading state (disabled + aria-disabled) during request
- [ ] Success path: toast notification + redirect to `/workflows`
- [ ] Error path: error toast displayed; button re-enabled; no uncaught exception
- [ ] Button hidden for non-client block types (deal, contact, project)
- [ ] Keyboard accessible: button reachable via Tab, activatable via Enter/Space
- [ ] Tested at 375px and 1280px; no layout shift when button appears

**Applicable Gates:** 1, 4, 5
**Dependencies:** none (POST /api/actions/onboarding.start DONE in P1-S1-BE-04; workflow engine DONE in P1-S2-BE-01)
**Complexity:** MEDIUM
**Estimate:** 2 days
**Assigned Role:** FRONTEND-ENGINEER

## P1-S3-BE-01: Production Cron Config + Engine Hardening

**Description:** Wire the workflow engine to Vercel's cron scheduler and fix the two Gate 6 findings from P1-S2-BE-01 peer review. The engine exists but jobs will never run automatically in production without the cron config. Both hardening fixes are correctness/security improvements that should land before external design partner traffic.

**Changes:**
1. `vercel.json` — add cron entry: `{ "path": "/api/workflow-engine/process", "schedule": "* * * * *" }` (every minute)
2. `src/app/api/workflow-engine/process/route.ts:20` — invert secret guard to fail-closed: `if (!secret || provided !== secret) → 401`
3. `src/lib/workflow/engine.ts` — `markDone` and `markFailed`: check Supabase `.update().eq()` return values; log `engine.db_update_failed` error event if update returns an error; do not emit success events if DB update failed

**Acceptance Criteria:**

- [ ] `WORKFLOW_ENGINE_SECRET` documented in `.env.example` with placeholder and description
- [ ] Cron secret guard is fail-closed: absent env var rejects all callers (not accepts all)
- [ ] `markDone` and `markFailed` check Supabase update return value; log error and return early if DB error
- [ ] Unit tests updated to cover: absent env var → 401, markDone DB error → no success event emitted

**Acceptance Criteria:**
- [ ] `assembleContext()` with `blockId = null` prepends org-level summary to context string

- [ ] Unit tests: org summary present in null-blockId context, edge context present when edges exist, edge context absent when no edges
- [ ] `assembleContext()` performance: no additional DB round-trips beyond existing 3 queries (batch with existing calls)

**Description:** Playwright E2E test covering the full path that a design partner will follow: navigate to a client block → trigger onboarding → verify workflow job created → poll until done → verify events populated. This is the first E2E test that exercises the actual business flow end-to-end, not just the auth smoke test.

**Test flow:**
1. Sign in (existing E2E_CLERK_EMAIL credentials)
2. Navigate to `/blocks` → find a client-type block
3. Click "Start Client Onboarding" button
4. Assert: toast notification appears
5. Navigate to `/workflows`
6. Poll every 2s for up to 30s: assert job transitions from `pending` → `done`
7. Navigate back to block detail
8. Assert: new events present (document.requested, kyc.check.started, aml.check.started)
