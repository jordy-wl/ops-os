## P1-S2-BE-01: Workflow Engine — Postgres Job Queue Processor

**Description:** Implement the workflow engine that processes `workflow_jobs`. Sprint 1 created the schema and action handlers that enqueue jobs; Sprint 2 delivers the processor that actually runs them. Uses a Postgres-based polling loop (prototype-tier — not Temporal, acceptable for <100 concurrent workflows).

**Engine behaviour:**
- Poll `workflow_jobs WHERE status = 'pending' AND scheduled_at <= NOW()` every 5 seconds
- Claim job: UPDATE status = 'running', claimed_at = NOW()
- Execute: dispatch to workflow handler based on `workflow_type`
- On success: UPDATE status = 'done', completed_at = NOW(); create `workflow.completed` event
- On failure: increment `attempts`; if attempts < 3 → reschedule (status = 'pending', scheduled_at = NOW() + interval '30s'); if attempts ≥ 3 → status = 'failed'; create `workflow.failed` event

**Sprint 2 workflow handlers:**
1. `onboarding` — logs each onboarding step as events (document.requested, kyc.check.started, aml.check.started)

**Acceptance Criteria:**
- [ ] `src/lib/workflow/engine.ts` — processor loop with claim + execute + status transition
- [ ] `src/lib/workflow/handlers/onboarding.ts` — onboarding workflow handler
- [ ] Workflow engine starts on Next.js app startup (or as a separate cron endpoint)
- [ ] Successful workflow creates `workflow.completed` event scoped to correct org
- [ ] Failed workflow after 3 attempts creates `workflow.failed` event
- [ ] `GET /api/workflow-jobs?status=pending` — list workflow jobs for org
- [ ] Database migration: add `claimed_at`, `completed_at` columns if not present
- [ ] Unit tests: claim job, success path, failure + retry logic, 3-strike fail
- [ ] Integration test: `onboarding.start` action → workflow_job created → engine picks it up → status = 'done'

**Applicable Gates:** 1, 2, 3, 5, 6
**Dependencies:** none (schema from P1-S1-BE-01 DONE; action handlers from P1-S1-BE-04 DONE)

- `ops-admin` — full access; can manage other users' roles
- `ops-user` — create/update blocks, trigger workflows, chat with AI

- [ ] `requireRole(role)` middleware for route-level enforcement
- [ ] `compliance-approver` blocked from POST /api/blocks and POST /api/actions → 403
- [ ] Unit tests: all 3 roles; default role assignment; role-blocked endpoint → 403

## P1-S2-AI-01: Semantic Search Integration in Context Assembly

**Description:** Wire the pgvector embedding search (DE-02 from Sprint 1) into the context assembly service. When assembling context for Claude, perform a semantic search for relevant historical events — not just the 20 most recent. This makes AI answers much better for long-running clients with many events.

**Enhanced context assembly:**
- Keep: last 10 chronological events (recency)
- Add: top 5 semantically similar events to the user's query (relevance)
- Total events in context: ≤15 (down from 20, but more relevant)

**Acceptance Criteria:**
- [ ] `assembleContext()` accepts optional `query: string` parameter
- [ ] When `query` provided: calls `match_embeddings()` RPC for top 5 similar events
- [ ] Combined events: deduplicated; labelled "recent" vs "relevant" in context string
- [ ] When `query` not provided: falls back to 20 most-recent behaviour (no regression)
- [ ] Unit tests: with query (semantic search called), without query (no semantic search)
- [ ] Semantic search failure (OpenAI unavailable): logs + falls back to recency-only (never throws)

**Applicable Gates:** 1, 2, 5
**Dependencies:** none (DE-02 search endpoint from P1-S1-DE-02 DONE)
**Complexity:** MEDIUM
**Estimate:** 1.5 days
**Assigned Role:** AI-ML-ENGINEER
