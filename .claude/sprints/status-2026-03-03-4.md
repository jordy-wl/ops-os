## What's Been Built

As of today, Ops OS is a live, deployed Business Operating System available at https://ops-os-gamma.vercel.app. Users can:

- Create and browse stateful Blocks (client entities, deals, counterparties) with a structured graph of relationships
- View a complete, immutable event timeline for any Block — every change is permanently recorded and timestamped
- Run AI chat against live operational data — the system assembles context from the Block graph, recent events, and semantic search before each conversation turn
- Monitor workflow job status — the system can process and track multi-step operational workflows via a Postgres job queue

The system supports multi-tenant auth with role-based access control (ops-admin, ops-user, compliance-approver) — meaning multiple client firms can each have their own isolated workspace.

## Infrastructure and Scalability

The current stack (Vercel edge functions + Supabase Postgres on ap-south-1) is designed for the prototype tier only. The Postgres workflow queue will not handle more than ~100 concurrent workflows reliably, and Vercel free tier limits apply. Phase 4 specifies a migration path to Temporal (durable workflow engine), Neon Postgres, and multi-region deployment — all scoped only after revenue justifies the investment. For the current design partner phase (2–5 firms, low concurrent usage), the infrastructure is sufficient without modification.

## AI/ML Bets

The system currently deploys Claude Sonnet (claude-sonnet-4-6) as the AI layer. The context assembly service draws from: Block graph traversal, recent event timeline, and pgvector semantic search over embedded event history. Current confidence: high that this generates useful operational context for chat; unproven that it reduces actual coordination time for a real user. Phase 2 introduces AI confidence routing — the system will score its own confidence on proposed actions and route to human approval when confidence falls below threshold. This is the key differentiator for capital markets compliance workflows where human sign-off is non-negotiable.

Cost structure: Claude API costs are usage-based; at prototype scale with 2–5 design partners, this is negligible. Phase 2 will require cost-per-workflow modelling before pricing decisions.

## Current Honest Limitations

- **No workflow trigger in the UI.** Users cannot start a workflow from the app today. This is the single biggest gap for design partner sessions — the Sprint 3 FE-01 task fixes this.
- **No AI-proposed actions.** The AI chat can discuss operations but cannot propose or execute workflow actions. This is Phase 2 scope.
- **Postgres queue is not durable.** If the server restarts mid-job, jobs may be lost. Acceptable at prototype scale; not acceptable for paying customers.
- **Only one proxy design partner session completed.** The Phase 1 exit condition requires 2+ real organisations each running 10+ workflows. Currently: 0 real external partners, 1 real event in production.
- **No audit export.** Compliance teams cannot export the event trail as PDF/JSON for regulatory requests. This is Phase 3 scope.
