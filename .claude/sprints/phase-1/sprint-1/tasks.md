## P1-S1-BE-01: Core Database Schema

**Description:** Create the foundational Supabase migrations for all 6 core tables. These tables are the data model of the entire product. Enforce immutability on `events` via Supabase RLS (deny UPDATE and DELETE). Enable RLS on all tables with org_id scoping.

**Tables:** `orgs`, `blocks`, `block_edges`, `events` (immutable), `workflow_jobs`, `embeddings`

**Key schema details:**
- `blocks.data JSONB` — flexible entity data (client name, AUM, etc.)
- `blocks.jurisdiction TEXT` — ISO code: "GB", "US", "SG", "HK", "AU"
- `events` — no `updated_at` column; RLS denies all UPDATE and DELETE
- `embeddings.embedding vector(1536)` — pgvector with ivfflat index
- All tables have `org_id UUID NOT NULL REFERENCES orgs(id) ON DELETE CASCADE`

**Acceptance Criteria:**
- [ ] All 6 tables created via Supabase migration file in `supabase/migrations/`
- [ ] `pgvector` extension enabled before embeddings table is created
- [ ] RLS enabled on all tables; org_id-based policy prevents cross-org data access
- [ ] Events table RLS policy denies UPDATE and DELETE for all roles including service role
- [ ] Indexes created: `blocks(org_id, type)`, `events(block_id, occurred_at)`, `events(org_id, occurred_at)`, `block_edges(from_block_id)`, `workflow_jobs(org_id, status, scheduled_at)`
- [ ] ivfflat index on `embeddings(embedding vector_cosine_ops)`
- [ ] Migration runs cleanly from `supabase db reset`

**Applicable Gates:** 1, 2, 5
**Dependencies:** P1-S1-OPS-01
**Complexity:** MEDIUM
**Estimate:** 2 days
**Assigned Role:** BACKEND-ENGINEER

## P1-S1-BE-02: Blocks API

**Description:** Implement the Blocks API in `/app/api/blocks/`. Blocks are the core business entities — clients, deals, projects, contracts. All mutations must create a corresponding event in the `events` table.

**Endpoints:**
- `GET /api/blocks` — list blocks for org (`?type=client&limit=50&offset=0`)
- `POST /api/blocks` — create a block (`{type, data, jurisdiction}`)
- `GET /api/blocks/:id` — get block with its last 20 events
- `PATCH /api/blocks/:id` — update block data (must write a `block.updated` event)
- `GET /api/blocks/:id/neighbours` — return all directly connected blocks (one-hop)
- `POST /api/blocks/:id/edges` — create a directed edge between blocks

**Acceptance Criteria:**
- [ ] All 6 endpoints implemented with correct HTTP status codes
- [ ] `GET /api/blocks/:id` returns block data AND last 20 events in one response
- [ ] `PATCH /api/blocks/:id` writes a `block.updated` event with the diff in payload
- [ ] `GET /api/blocks/:id/neighbours` returns all directly connected blocks in <200ms on local data
- [ ] All routes validate Clerk JWT and extract `org_id`; 401 if unauthenticated, 403 if wrong org
- [ ] Request bodies validated with Zod; 400 with field-level errors on invalid input
- [ ] Consistent response shape: `{data: ..., error: null}` or `{data: null, error: {message, code}}`
- [ ] Unit tests: create block, get block with events, update block (verifying event created), get neighbours

**Applicable Gates:** 1, 2, 3, 5
**Dependencies:** P1-S1-BE-01, P1-S1-BE-05
**Complexity:** MEDIUM
**Estimate:** 2 days
**Assigned Role:** BACKEND-ENGINEER

## P1-S1-BE-03: Events API

**Description:** Implement the Events API in `/app/api/events/`. Events are the immutable audit log — created only, never updated or deleted. The API surface is deliberately minimal. The `occurred_at` field is always set server-side.

**Endpoints:**
- `POST /api/events` — create an event (`{block_id?, event_type, payload, actor_type}`)
- `GET /api/events?block_id=:id` — list events for a block, desc by `occurred_at`, paginated
- `GET /api/events?org_id=:id&limit=100` — list recent events across the whole org

**Critical:** No PUT, PATCH, or DELETE endpoints for events — these must not exist anywhere.

**Acceptance Criteria:**
- [ ] `POST /api/events` creates an event with `occurred_at` set server-side; returns 201
- [ ] `GET /api/events?block_id=:id` returns events sorted `occurred_at` DESC with cursor pagination
- [ ] No UPDATE or DELETE endpoints exist in the codebase for events
- [ ] Integration test verifies: create event → attempt direct PATCH via Supabase client → RLS denies it
- [ ] `actor_id` always set from Clerk JWT, never from request body
- [ ] Unit tests: create event, list events, pagination

**Applicable Gates:** 1, 2, 3, 5
**Dependencies:** P1-S1-BE-01, P1-S1-BE-05
**Complexity:** MEDIUM
**Estimate:** 2 days
**Assigned Role:** BACKEND-ENGINEER

## P1-S1-BE-04: Actions API Skeleton

**Description:** Implement the Actions API — the command pattern gateway for all controlled mutations. Each action type has a registered handler and a risk level. Sprint 1 delivers the registry and two action types: `block.create` and `onboarding.start`.

**Architecture:**
```
POST /api/actions/:type
→ Validate auth + org
→ Look up handler in action registry
→ Validate payload against action schema (Zod)
→ Execute handler (mutate blocks + create events + optionally enqueue workflow_job)
→ Return: { actionId, eventId, workflowJobId?, status: "executed" }
```

**Action types for Sprint 1:**
1. `block.create` — creates a new block + records `block.created` event
2. `onboarding.start` — creates a `client` block + enqueues `onboarding` workflow_job + records `onboarding.started` event

**Acceptance Criteria:**
- [ ] `POST /api/actions/block.create` creates block + event atomically
- [ ] `POST /api/actions/onboarding.start` creates client block + workflow_job + event in sequence
- [ ] Action registry pattern: adding new action = handler file + registry entry (documented)
- [ ] All actions require auth; org_id scoped
- [ ] Action payloads validated with Zod per action type
- [ ] Response includes `eventId` and `workflowJobId` where applicable
- [ ] Unit tests: happy path for both actions, invalid payload 400, wrong org 403
- [ ] Integration test: `onboarding.start` → verify workflow_job row with `status = "pending"`

**Applicable Gates:** 1, 2, 3, 5, 6
**Dependencies:** P1-S1-BE-01, P1-S1-BE-02, P1-S1-BE-03
**Complexity:** HIGH
**Estimate:** 3 days
**Assigned Role:** BACKEND-ENGINEER

## P1-S1-AI-02: Context Assembly Service

**Description:** Build the context assembly service — given a `block_id` and `org_id`, assemble all relevant context for Claude. Sprint 1 uses 2 of 4 memory types: Working (block data) and Episodic (recent events). Semantic and Procedural memory deferred to Phase 2.

**Output:** Structured context object + `contextToPromptString()` formatter

**Context assembled:**
1. Working memory: block data + type + jurisdiction
2. Episodic memory: last 20 events on the block (configurable `MAX_CONTEXT_EVENTS = 20`)
3. Graph context: names and types of directly connected blocks (one hop)
4. Org context: org name + current user role

**Acceptance Criteria:**
- [ ] `assembleContext(blockId, orgId, userId)` exported from `lib/context-assembly.ts`
- [ ] Returns `{ block, events[], neighbours[], org, userRole }`
- [ ] `contextToPromptString(context)` formats context for Claude system prompt
- [ ] When `blockId` is null: assembles org-level context (recent events across all blocks)
- [ ] Total context ≤8000 tokens (rough character count guard)
- [ ] Unit tests: context for block with events, block with no events, null blockId

**Applicable Gates:** 1, 2, 5
**Dependencies:** P1-S1-BE-01, P1-S1-BE-02, P1-S1-BE-03
